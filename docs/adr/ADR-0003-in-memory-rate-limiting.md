# ADR-0003: Использование in-memory хранилища для Rate Limiting

**Статус:** Принято (Accepted) — временное решение для PoC
**Дата:** 13.11.2026

## Контекст
Для защиты от брутфорса и простого флуда был внедрен Rate Limiting на базе алгоритма «скользящее окно» (sliding window). Встал вопрос выбора бэкенда для хранения счетчиков.

## Решение
Использовать структуру `collections.deque` в оперативной памяти процесса Python (FastAPI). Лимиты сбрасываются при перезапуске контейнера.

## Последствия
- ✅ **Плюсы:** Нулевые накладные расходы, отсутствие внешних зависимостей. Идеально для локального запуска через `docker-compose` в одном экземпляре.
- ⚠️ **Минусы:** Решение не масштабируется. При горизонтальном масштабировании (запуск нескольких реплик за балансировщиком) каждый экземпляр будет считать лимиты независимо. Также счетчики сбрасываются при рестарте, что позволяет атакующему обойти лимиты, спровоцировав падение контейнера.

## Рассмотренные альтернативы
- **Redis (Token Bucket / Sliding Window):** Правильное решение для Production. Внедрение вынесено в Roadmap (P1), так как требует добавления нового контейнера в инфраструктуру и настройки сети.
