# ADR-0002: Политика отказов (Fail-open vs Fail-closed) для разных слоев

**Статус:** Принято (Accepted), частично пересмотрено
**Дата:** 12.11.2026

## Контекст
При построении эшелонированной обороны встает вопрос: как должна вести себя система, если один из защитных компонентов падает или недоступен? В проекте исторически сложилось два разных подхода: Presidio (PII) возвращал `False` при ошибке (пропускал запрос), а LLM-судья — блокировал (Fail-closed).

## Решение
1. Для **LLM-судьи** (семантическая проверка) выбран строгий **Fail-closed**: если судья недоступен, вернул невалидный JSON или упал по таймауту — ответ блокируется.
2. Для **Presidio** (детектор PII) изначально был выбран **Fail-open** для упрощения отладки PoC, чтобы падение тяжелой ML-модели не блокировало весь шлюз.

## Последствия
- ✅ **Плюсы:** В случае с судьей мы гарантируем, что подозрительный контент не уйдет пользователю при сбое инфраструктуры.
- 🚨 **Минусы (Критично):** Fail-open в Presidio — это уязвимость. Если анализатор не инициализирован, система пропускает PII. При подготовке к ревью это было признано проблемой уровня **P0**.
- 🔧 **Текущий статус:** Внедряются статусы `PASS/BLOCK/ERROR`. Для критичных слоев (включая PII) политика меняется на Fail-closed с метрикой деградации `gateway_degraded_total`.
